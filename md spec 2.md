# Техническое задание: Страница "Обработка заказов" (FBS Ozon + Wildberries)

## 1. Общее описание

Расширение существующего веб-приложения (парсер остатков тканей, см. базовый ТЗ проекта) новой страницей **"Обработка заказов"**. Страница собирает через API текущие FBS-заказы с маркетплейсов Ozon и Wildberries, заменяет артикул маркетплейса на артикул поставщика (по файлу `mapping.xlsx`, уже используемому в проекте) и группирует результат по поставщикам — чтобы оператор мог одной кнопкой скопировать список артикулов для конкретного поставщика и отправить его на отгрузку.

Технологический стек, аутентификация, стиль хранения конфигурации и общая структура сайта — **те же, что описаны в базовом ТЗ проекта**. Ниже описывается только новый функционал.

## 2. Расположение в структуре сайта

Добавляется третий роут:

- `/orders` — страница "Обработка заказов".

Пункт добавляется в общую навигацию (шапка/сайдбар) рядом с существующими `/parser` и `/stickers`.

## 3. Источник соответствия артикулов

Используется **тот же файл `mapping.xlsx`**, что загружен и хранится для страницы "Парсер" (`storage/mapping.xlsx`), новый отдельный файл не требуется.

### 3.1. Структура листов mapping-файла

| Лист | Поставщик | Колонки |
|---|---|---|
| `GT_Byaz_220_120`, `GT_Byaz_220_140`, `GT_Byaz_150_120`, `GT_Byaz_150_140`, `GT_Poplin_220` | Galtex | A: артикул маркетплейса, B: артикул поставщика, C: баркод ВБ |
| `GT_Byaz_150_120_Solid`, `GT_Byaz_150_140_Solid` | Galtex (однотон) | A: артикул маркетплейса, B: артикул поставщика, C: баркод ВБ |
| `TD` | ТексДизайн | A: артикул маркетплейса, B: артикул поставщика, C: баркод ВБ |
| `AD` | АртДизайн | A: артикул маркетплейса, B: название товара, C: артикул поставщика, D: баркод ВБ |
| `TDL_Byaz_220_solid` | ТДЛ | A: артикул маркетплейса, B: артикул поставщика |
| `TT` | Традиции Текстиля | A: артикул маркетплейса, B: артикул поставщика, C: баркод ВБ |
| `LB` | ЛогатексПРО | A: артикул маркетплейса, B: артикул поставщика, C: баркод ВБ |

**Важно:** для страницы "Обработка заказов" из mapping-файла используется **колонка A** каждого листа — это "Артикул на маркетплейсе" в терминологии данной задачи (полный код вида `GT-220120-BZ-8-TropicanaBlack`, `TDL-220120-M-PP-33-Green` и т.п.), по которому мы делаем поиск. Колонка B (у всех кроме AD, у AD это колонка C) - это "артикул поставщика", именно это значение используется для формирования списка товаров на отправку поставщику.

### 3.2. Определение поставщика по артикулу

Поставщик определяется по префиксу артикула поставщика (часть строки до первого `-`):

| Префикс | Поставщик |
|---|---|
| `GT` | Galtex |
| `TD` | ТексДизайн |
| `QUM` | КумТекс |
| `AD` | АртДизайн |
| `TT` | ТрадицииТекстиля |
| `LTP` | ЛогаТексПРО |
| `TDL` | ТДЛ |
| `CHN` | Чаншу |
| `LT` | ЛакиТекс |

Список префиксов вынести в конфиг (константа/JSON), чтобы можно было добавлять новых поставщиков без правки кода.

Помимо этого в заказах могут встречаться такие префиксы как `SHF`, `DC`, `PC` - это постельное белье. Необходимо выносить эти заказы в отдельную секцию "Постельное белье"
Так же есть товары с префиксом `MT` - это лента для герметизации швов 

### 3.3. Поиск соответствия

Т.к. на этапе получения заказа неизвестно, к какому поставщику относится артикул, поиск выполняется **по всем листам mapping-файла** (полный перебор строк всех 12 листов), пока не найдено совпадение значения из колонки A с артикулом заказа. Если совпадение найдено на нескольких листах одновременно — это ошибка данных, логировать предупреждение и использовать первое найденное совпадение.

Если совпадение **не найдено** ни на одном листе — товар всё равно отображается в итоговой таблице, но:
- артикул поставщика показывается как `—` / "Не найдено соответствие";
- строка попадает в отдельную группу **"Без сопоставления"** (не удаляется из выдачи, чтобы заказ не потерялся).

## 4. Получение заказов

Один общий элемент управления — кнопка **"Получить заказы"**. По нажатию:

1. Блокируется кнопка, показывается индикатор загрузки.
2. Backend параллельно запрашивает заказы у Ozon и у WB.
3. Полученные позиции сопоставляются с mapping-файлом (п. 3.3).
4. Результат группируется и выводится в таблицу (п. 6).
5. Если один из маркетплейсов недоступен (ошибка API/сети) — обработка второго маркетплейса продолжается, в UI отображается предупреждение по недоступному маркетплейсу (аналогично статусам ошибок в блоке парсера остатков), без прерывания всего процесса.

### 4.1. Ozon — FBS-заказы "Ожидает сборки"

- Endpoint: Ozon Seller API, метод получения списка отправлений FBS (`/v3/posting/fbs/list` или актуальный аналог) с фильтром `filter.status = awaiting_packaging`.
- Авторизация: заголовки `Client-Id` и `Api-Key` (значения — из конфига, см. п. 8).
- Из каждого отправления (posting) извлекаются:
  - номер отправления (`posting_number`);
  - список товарных позиций, для каждой — артикул продавца (`offer_id`) и количество в позиции заказа.
- **Уточнить при реализации:** точную версию эндпоинта и структуру ответа по актуальной документации Ozon Seller API на момент разработки (метод мог измениться); при пагинации — обойти все страницы результата (`limit`/`offset` или `cursor`, в зависимости от версии API).

### 4.2. Wildberries — FBS-заказы "Новый"

- Endpoint: WB Marketplace API, метод получения новых заказов (`GET /api/v3/orders/new` или актуальный аналог для статуса "Новый").
- Авторизация: заголовок `Authorization` с токеном продавца (из конфига).
- Из каждого заказа извлекаются:
  - номер заказа WB (`orderId` / `id`, используется как аналог "номера отправления" для WB);
  - артикул продавца (`article` / `supplierArticle` — поле, соответствующее артикулу маркетплейса, единому с Ozon);
  - количество — если API возвращает заказы поштучно (по одному товару на заказ, как обычно у WB), количество = 1 на строку, суммируется при группировке (см. п. 5).
- **Уточнить при реализации:** точное имя поля с артикулом продавца в ответе API (может называться `article`, `supplierArticle` или `nmId`+сопоставление номенклатуры — зависит от актуальной версии API); при необходимости — обойти пагинацию.

## 6. Группировка и отображение

### 6.1. Дедупликация по артикулу

Строки группируются по `marketplaceArticle`:

- если один и тот же артикул встречается в нескольких отправлениях — в таблице выводится **одна строка**;
- в строке указывается суммарное количество (**"Кол-во"**) и список всех номеров отправлений, в которых встретился артикул (через запятую, с возможностью показать/скрыть при большом количестве, для Озон в начало каждого номера отправления добавляется OZN, для отправлений с ВБ добавляется WB);
- если артикул встретился один раз — количество = 1, показывается один номер отправления.

### 6.2. Структура таблицы

Колонки итоговой таблицы:

| Артикул маркетплейса | Артикул поставщика | Кол-во | Номера отправлений |
|---|---|---|---|
| ... | ... (или "—") | ... | ... |

### 6.3. Группировка по поставщикам

Таблица разбивается на блоки/аккордеоны по поставщику (определённому в п. 3.2), в порядке: Galtex, ТексДизайн, КумТекс, АртДизайн, ТрадицииТекстиля, ЛогаТексПРО, ТДЛ, Чаншу, ЛакиТекс, затем отдельный блок **"Без сопоставления"** — для строк, где артикул поставщика не найден. В блоке **Без сопоставления** указываются артикулы маркетплейса.

В заголовке каждого блока-поставщика — название поставщика и общее количество позиций/суммарное количество единиц товара.

### 6.4. Кнопка копирования артикулов поставщика

В каждом блоке-поставщике — кнопка **"Скопировать артикулы поставщика"**, которая копирует в буфер обмена список артикулов поставщика этого блока, по одному на строку (перенос строки `\n`), с учетом количества (если артикул заказан 1 раз, то через пробел писать **Кол-во: 1шт**, если же больше, указывать конкретное количество **Кол-во: Nшт**)

## 7. UI-блок страницы

1. Кнопка **"Получить заказы"** (вверху страницы), с индикатором загрузки и блокировкой на время запроса.
2. Строка статуса по каждому маркетплейсу после получения ("Ozon: получено N заказов" / "Ozon: ошибка — текст ошибки", аналогично для WB).
3. Сводная таблица заказов, сгруппированная по поставщикам согласно п. 6.3, с кнопками копирования по каждому поставщику (п. 6.4).
4. Данные заказов **не сохраняются на сервере** между сессиями — хранятся только в состоянии фронтенда до повторного нажатия "Получить заказы" или обновления страницы (аналогично логике незагружаемых на сервер файлов остатков в текущем ТЗ).

## 8. Хранение конфигурации (API-ключи маркетплейсов)

Дополнение к существующему файловому JSON-конфигу (`config/settings.json`):


```json
{
  "marketplaceApi": {
    "ozon": {
      "clientId": "",
      "apiKey": ""
    },
    "wb": {
      "apiToken": ""
    }
  }
}
```

- Отдельный блок настроек на странице с полями ввода Client-Id/Api-Key для Ozon и токена для WB, сохранение через `POST /api/config/marketplace-api` (аналогично уже существующим ручкам сохранения конфига в базовом ТЗ).
- Значения не выводятся в открытом виде после сохранения (поле типа password / маскировка), только индикатор "ключ сохранён".
- **Важно**: Необходимо хранить ключ в .env файле. Если ключ изменен, перезаписывать значение в .env файле. 

## 9. Backend API (новые эндпоинты)

- `GET /api/config/marketplace-api` — получить текущие сохранённые настройки (без раскрытия полных значений ключей, только маска/факт наличия).
- `POST /api/config/marketplace-api` — сохранить/обновить Client-Id/Api-Key Ozon и токен WB.
- `POST /api/marketplace/orders/fetch` — запускает получение заказов с Ozon и WB, сопоставление с mapping-файлом, возвращает готовую сгруппированную структуру для отображения (см. п. 5–6). Ответ включает статус по каждому маркетплейсу (`success`/`error` + текст ошибки), чтобы UI мог отобразить частичный успех.

## 10. Обработка ошибок

- Ошибка авторизации/сети по одному маркетплейсу не должна прерывать обработку второго.
- Артикул без соответствия в mapping-файле не исключается из выдачи (см. п. 3.3), а попадает в отдельную группу "Без сопоставления", чтобы ни один заказ не был потерян из виду оператором.
- Если mapping-файл не загружен на сервере при попытке получить заказы отображается ошибка "Mapping-файл не загружен, сопоставление артикулов невозможно", запрос к API маркетплейсов не производится.

## 11. Прочие технические требования

- Backend-логика получения и сопоставления заказов — на TypeScript, со строгой типизацией моделей в общем стиле с остальным проектом.
- Frontend-компоненты — React + TypeScript
- Дизайн в едином стиле с остальным приложением - Human Interface Guidelines (HIG).
- Персистентность на фронте не требуется — данные заказов держатся в состоянии до обновления страницы.
